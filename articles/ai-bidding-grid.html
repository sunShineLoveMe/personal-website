让大模型参与招投标：
一个电力行业标书工作台的产品拆解

标书不是写作比赛。真正的设计重心是解读、检索、约束和核对，并让人始终在回路里。

作者：Chris约 18 分钟阅读4 张图 · 1 张表

ABSTRACT

本文拆解一个面向电力行业的 AI 标书工作台（开源仓库 ai_bidding_power_grid），讨论：

  1. 为什么它停在“起草，由人审阅”，而不是全自动；
  2. 解读、检索、写作、合规复核四个环节各自的设计取舍；
  3. 用方法论一文的框架审视它：目前缺少什么评测，下一步该补什么。

文中的事实来自该仓库的 README 与评估报告，产品分析为作者判断。

01标书不是写作比赛

让大模型写一份标书，第一反应是“文笔够不够好”。做过投标的人都知道，这不是难点。

标书的难，在于它同时要满足三件事：响应招标要求，不能漏项，实质性条款不满足通常会直接导致投标被否决；对照评分办法得分，每个评分项都要有对应的内容与证据；内容必须真实，资质、业绩、参数不能编。三件事里没有一件是“写得漂亮”能解决的。

这决定了这类产品的设计重心：不是把生成文字这一步做得多强，而是把解读、检索、约束、核对这几件事串成一条可检查的流水线，并让人始终待在回路里。下面拆解的，是我做的电力行业 AI 标书工作台。它面向电力工程、设备供货和运维服务企业，把招标文件、企业知识库和标书编写放在同一个工具里。[1]

本文的边界

仓库的 README 明确声明：AI 输出需结合原始招标文件和企业材料复核，合规检查只用于辅助编制，不保证中标，也不替代投标人的最终审核。[1] 下面所有设计，都建立在这个前提上。

02先划边界：它做什么，不做什么

在方法论文章里我讲过，AI 产品要先决定自主权档位。这个工具的选择很清楚：停在“起草，由人审阅”这一档，而不是“全自动出标书”。原因有三条，都来自业务本身：

  • 出错代价高，而且不易被察觉。漏掉一条实质性要求，不会在生成当时报错，却可能在评标时让整份投标失去资格。这正是方法论里“代价高、难发现”的象限，只适合做草稿加确认。
  • 责任不能转移。投标人对标书内容负责，工具给出的是编制辅助，最终的签章和审核必须是人。
  • 材料有边界。README 建议先导入脱敏的资信或产品材料，实际业务中应使用有权处理的企业资料。[1]

因此，这个产品的价值不是“替你投标”，而是把一份几十页的招标文件，变成一张可核对的清单，再把写作和检查的体力活压缩下来。

03总流程：六个环节，四个人工检查点

README 推荐的首次体验路径，本身就是一条带检查点的流水线：先在系统设置里填写企业画像并导入脱敏材料；上传招标文件，检查解析出的要求、评分项与风险；生成分册大纲，选择章节生成正文并在编辑器里修改；最后查看响应覆盖和 AI 用量记录，再导出 DOCX。[1]

注意检查点的位置：它们都放在上一个环节的输出被下一个环节“信以为真”之前。解读如果错了，后面的大纲、正文、合规检查会一路错下去，所以第一个检查点最贵、也最值得投入。

04解读：把长文件变成结构化清单

解读环节的产出是后面所有环节的“真相来源”。按仓库里一份评估报告的描述，系统会从招标文件中抽取六类信息：项目概况、资格要求、商务要求、技术要求、评分项和风险项；遇到扫描件、图片和复杂表格，则可借助 MinerU 做 OCR。[2]

从产品角度看，这一步有两个设计要点：

  • 结构化，而不是摘要。摘要读起来舒服，却没法被逐项核对；“要求、评分项、风险项”这样的清单，才能在后面作为合规检查的对照基准。
  • 让人能快速纠错。解析结果要以易于核对的形式呈现，并允许修改。扫描件识别需要额外配置 MinerU，这是一个现实的依赖，也是一个需要在文档里讲清楚的限制。[1]

05检索：企业资料不是“搜到”就行

标书里最不能出错的，是企业自己的事实：资质、业绩、产品参数、型号。这些内容应当来自知识库，而不是模型的“记忆”。README 里的知识库检索，使用向量召回、Rerank 和关键词兜底三层。[1]

为什么需要第三层？仓库里的评估报告在评审一个早期版本时指出，只用向量检索会丢失领域术语和型号，并建议加入关键词检索与重排。[2] 这个判断很符合直觉：向量擅长“意思相近”，却不擅长“必须一字不差”。设备型号、条款编号、证书号恰恰是后者。目前 README 列出的能力已经包含重排与关键词兜底，方向与那份评审的建议一致。

产品判断

检索的目标不是“找到相关内容”，而是“找到可以被引用的事实”。所以进入写作提示的资料应当带来源，让人在审阅时能回到原文核对。

06写作：用规则约束模型

评估报告把“规则化的写作计划”列为这个系统的亮点之一：系统会为每个章节计算目标字数和建议页数，并决定是否需要插入表格、图片、资质或案例，用规则去约束模型的输出，而不是完全交给模型自由发挥。[2]

这背后是一条通用的方法：能写成规则的约束，就别指望模型自觉遵守。篇幅、结构、必须出现的元素，这些是确定性的要求，用代码规划；模型只负责在这个框架里把内容写得通顺、贴合资料。

长章节怎么写

报告提到，对超过 3,500 字的核心章节，系统采用多轮生成，以避免输出被长度上限截断；正文通过流式方式返回，用户不必等到整章生成完才能看到内容。[2]

一个已知的风险：上下文污染

评估报告同时指出，早期版本会把前面章节的内容不加裁剪地喂给模型，长篇生成时可能出现上下文污染、token 浪费和注意力被稀释的问题，并建议用摘要或记忆机制压缩前文。[2] 这个风险在长文本产品里很典型：文档越长，越需要主动管理“模型此刻该看到什么”。

07合规复核：从“找得到”到“对不对”

合规复核是这个产品最贴近风险的一环。评估报告对早期版本的评价是：合规检查主要靠文本匹配，只能做粗粒度比对，难以判断语义上是否真正响应；建议升级为用 LLM 做语义交叉核对。[2] README 现在的描述是“规则检查加 LLM 语义复核，定位响应缺失并给出补强建议”。[1]

两层各有分工。规则检查是确定性的：要求里的某个关键项，在正文里出现了吗？语义复核则回答更难的问题：正文里提到了，是不是真的满足了要求？只有前一层，会把“提到了”误当成“响应了”；只有后一层，则会让结果难以复现。

08成本与追踪：把账放进产品

标书是大批量长文本生成的典型场景：一份标书几十个章节，每个章节都可能多轮生成，还要检索和复核。README 把“任务记录、模型调用用量与成本记录”作为交付与追踪的一部分。[1]

这不是锦上添花。没有用量与成本记录，就无法回答“一份标书的真实成本是多少”，也就无法决定怎么定价、该不该换模型、缓存是否值得。这部分的分析，我放在了《AI 产品的定价与成本账》里。

09用评测的眼光看：它还缺什么

这是我对这个项目最诚实的一节。README 没有给出量化的效果指标或基准结果；那份评估报告也只是基于代码走查的定性评价，同样没有基准和测试数据。[1][2] 换句话说：它有流程设计，但还没有一套能反复运行的评测集。按方法论一文的框架，下一步应该补的是下面这些检查项。

检查项类型怎么判为什么重要
引用的资质、业绩、型号是否都存在于知识库硬约束代码比对标书里不能编造事实
解读是否覆盖了招标文件中的全部评分项硬约束人工标注清单 + 代码比对解读是后续所有环节的基准
实质性要求是否都得到响应硬约束语义复核 + 抽样人工漏项可能导致被否决

长章节在多轮生成后是否前后一致软质量抽样人工对应上下文污染的风险

10局限与风险

  • 没有量化指标。目前无法用数字说明它“好到什么程度”，这是上一节要补的。
  • 保密与隐私。招标与企业资料往往涉及商业秘密。评估报告本身没有讨论安全、隐私与保密，这是一个明显的空白；README 提示使用脱敏材料、部署时替换示例密钥，只是起点。[1][2]
  • 依赖外部服务。默认使用 DeepSeek 做写作与解读，知识库依赖 DashScope 的 Embedding 与 Rerank，需要同时配置相应的密钥，服务的可用性和成本变化都会影响产品。[1]
  • 不是中标保证。投标的结果取决于许多工具之外的因素。这个产品能减少漏项和体力劳动，不能替代对项目本身的判断。

11如果重新做一遍，我会先做什么

  1. 收集几十份脱敏的真实招标文件，人工标注评分项与实质性要求，作为第一版评测集。
  2. 把“解读是否覆盖全部评分项”变成每次改动都要跑的回归检查。
  3. 给知识库中的每条事实标注来源，并让写作提示强制引用来源。
  4. 为合规复核设定“宁可多报，不可漏报”的阈值，并由业务方拍板。
  5. 从第一天起记录每个环节的用量与成本，用它倒推定价。
